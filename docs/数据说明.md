# 生产制造模拟器数据说明

> 适用目录：`/home/lpw/production_simulator/datasets`  
> 数据快照：2026-11-23  
> 适用对象：模拟器开发、算法接入、前端展示、异常检测联调和数据维护人员

## 1. 文档目的与范围

本文说明生产制造模拟器当前使用的数据目录、文件格式、字段含义和运行关系，重点回答两个问题：

1. 模拟器当前包含哪些数据；
2. 每种数据分别表示什么，以及在模拟器中承担什么作用。

本文只说明**输入数据和与之配套的元数据**。仿真运行后产生的 `log/latest/`、`result_schedule.csv`、`gantt_chart.txt` 等输出文件不在本文范围内。

## 2. 总体结论

当前数据可以分为三类：

| 类别 | 数据 | 当前规模 | 主要用途 |
| --- | --- | ---: | --- |
| 运行时核心数据 | 四工艺 FJSP、加工能耗、运输、交付、物料库存与消耗 | 309 组四工艺实例 | 生成 Job、Task、Machine，并驱动调度、能耗、交付和物料事件 |
| 运行时扩展数据 | 设备传感器流数据 | 15 台预生成机器 | 设备状态展示、异常检测和故障预警 |
| 元数据与辅助数据 | 数据清单、生成配置、生成脚本、产品配置样例 | 与核心数据配套 | 追溯生成过程、校验数据、维护和复现 |

需要注意以下统计口径：

- 当前实际可用、可在 Web 页面选择和运行的 FJSP 实例是 **309 组**。
- `manifest.json` 保留了原始转换过程的信息，其中 `summary.total_instances` 为 550，包含 241 个 JSP 和 309 个 FJSP 候选；当前 `raw/`、`add/` 等运行时目录中的文件只对应 309 个 FJSP 实例。
- 设备数据服务随包附带 `machine_0.csv` 至 `machine_14.csv` 共 **15 台机器**；请求不存在的机器编号时，服务可以按确定性规则继续生成。
- `data_103.csv` 是车型和颜色等产品配置样例，当前主模拟器代码没有读取它，不应把它当作运行时 BOM 或订单数据。

### 2.1 数据流

```text
raw*/ + add*/
    └─ 调度工艺、加工时间、加工能耗、运输时间和运输能耗
delivery_cost/
    └─ Job 优先级、就绪时间、交期和提前/延期成本
material_consumption/ + material_configs/ + material_master.csv
    └─ Job/Task 物料需求、机器初始库存、物料名称和单位
            │
            ▼
simulator/dataset.py → Simulator → Job / Task / Machine / 事件队列
            ▲
            │ HTTP
simulator-data/
    └─ 设备传感器窗口、故障标签、预警标签
```

## 4. 四工艺调度数据

### 4.1 工艺映射

| 工艺编号 | 工艺 | 路由/加工时间目录 | 能耗/运输目录 | 每 Job Task 数 | 实例机器数范围 | 检测时间起点 |
| --- | --- | --- | --- | ---: | ---: | ---: |
| 1 | 冲压 | `raw/` | `add/` | 不固定 | 4–18 | 0 |
| 2 | 焊装 | `raw1/` | `add1/` | 固定 6 | 5–8 | 1800 |
| 3 | 涂装 | `raw2/` | `add2/` | 固定 6 | 4–7 | 3600 |
| 4 | 总装 | `raw3/` | `add3/` | 固定 8 | 6–10 | 5400 |

当前 309 个实例覆盖：

- Job 数：6–30；
- 冲压 Task：每 Job 3–25；
- 完整四工艺链：每 Job 23–45 个 Task；
- 数据来源族：Hurink、Barnes、Dauzère、Brandimarte。

冲压路线直接继承原始 FJSP 基准实例；焊装、涂装和总装分别使用固定的 6、6、8 道工艺模板。后三工艺通过产品变体、时间比例、能耗比例、机器系数和物料 BOM 形成不同 Job 的差异。

### 4.2 机器编号规则

- 每个工艺文件内部使用**从 1 开始**的本地机器编号。
- 四工艺加载到同一模拟器后，会按冲压、焊装、涂装、总装的顺序拼接为全局机器编号。
- Job 和 Task 内部保存的加工时间、能耗及运输矩阵使用全局机器编号，同时保留 `stage_id` 和 `stage_operation_id` 描述所属工艺和阶段内工序。

设前三个工艺机器数分别为 `M1`、`M2`、`M3`，则：

```text
冲压全局机器：1 .. M1
焊装全局机器：M1+1 .. M1+M2
涂装全局机器：M1+M2+1 .. M1+M2+M3
总装全局机器：M1+M2+M3+1 .. 总机器数
```

设备检测服务使用本地 `machine_id`，接入模拟器时会再加上目标工艺的 `machine_offset`，因此检测卡片上的本地机器 ID 与调度时间轴上的全局机器 ID 不能混用。

### 4.3 `raw*.fjs`：工艺路由与加工时间

第一行为实例头：

```text
num_jobs num_machines metadata
```

后续每个 Job 占一行：

```text
operation_count
  option_count machine_id processing_time
  option_count machine_id processing_time
  ...
```

由于整个 Job 写在同一行，实际文本形如：

```text
3 2 1 5 3 7 1 4 8 2 2 6 4 9
```

字段含义：

| 字段 | 含义 |
| --- | --- |
| `num_jobs` | 当前实例的 Job 数 |
| `num_machines` | 当前工艺的本地机器数 |
| `metadata` | 原始基准文件保留的附加整数，不作为生产 KPI |
| `operation_count` | 当前 Job 在本工艺中的 Task 数 |
| `option_count` | 当前 Task 可选机器数 |
| `machine_id` | 当前工艺的本地机器编号，从 1 开始 |
| `processing_time` | 指定机器加工该 Task 所需的仿真时间 |

同一个 Task 可以有多个机器选项，表示柔性作业车间中的可替代设备能力。加工时间以**仿真时间单位**计，不直接对应现实秒、分钟或小时。

### 4.4 `add*.fjs`：加工能耗与运输

`add`、`add1`、`add2`、`add3` 各包含三部分：

1. 前 `num_jobs` 行：与 `raw*.fjs` 的 Job/Task/机器选项逐项对齐的加工能耗；
2. 接下来 `num_machines` 行：运输时间矩阵；
3. 最后 `num_machines` 行：运输能耗矩阵。

加工能耗行的结构与 raw 路由完全相同，只是每台机器后面的第二个数值由“加工时间”变为“加工能耗”。加载器会校验 raw 与 add 的 Job 数、Task 数、机器选项集合是否一致。

运输矩阵表示**同一工艺内部**从一台机器转运到另一台机器的时间和能耗：

- 行为源机器，列为目标机器；
- 大小为 `num_machines × num_machines`；
- 对角线为 `0`；
- 矩阵对称，即 `time[a][b] = time[b][a]`；
- 跨工艺运输不写进阶段矩阵，由模拟器固定补充：冲压→焊装 `2`、焊装→涂装 `4`、涂装→总装 `3` 个仿真时间单位。

能耗字段使用相对 `energy_unit`，用于多目标优化比较，不应解释为实际 kWh、焦耳或设备铭牌功率。

### 4.5 `delivery_cost/*.fjs`：交付参数

四个工艺共享同一份交付文件。文件首行是注释：

```text
# priority ready_time due_time earliness_cost tardiness_cost
```

之后每个 Job 一行，行序与 raw 中的 Job 顺序一致：

```text
priority ready_time due_time earliness_cost tardiness_cost
```

| 字段 | 含义 |
| --- | --- |
| `priority` | Job 权重；数值越大，该 Job 的交付结果越重要 |
| `ready_time` | Job 最早可投产时间 |
| `due_time` | 计划交付时间；按完整四工艺链估算 |
| `earliness_cost` | 每提前 1 个时间单位的成本系数 |
| `tardiness_cost` | 每延期 1 个时间单位的成本系数 |

交付成本按下式计算：

```text
delivery_cost = priority × (
    earliness × earliness_cost
    + tardiness × tardiness_cost
)
```

其中 `earliness` 和 `tardiness` 以 Job 完成总装并达到交付状态后的实际时间为准。`due_time` 综合考虑四工艺加工、阶段内运输、机器排队缓冲和工艺间运输，并预留约 50% 的调度缓冲。

### 4.6 `process_generation_configs/`：生成过程配置

该目录按 `process_1` 至 `process_4` 保存每个实例的逐工艺生成配置，主要用于追溯和复现。

核心字段：

| 字段 | 含义 |
| --- | --- |
| `instance`、`process_id`、`process_name` | 实例和工艺标识 |
| `num_jobs`、`num_machines`、`num_operations` | 规模统计 |
| `rules` | 时间/能耗比例、机器系数和确定性种子规则 |
| `jobs[].job_id` | Job 编号 |
| `jobs[].variant` | 动力类型、驱动、车身颜色、车顶颜色、双色标志和冲压板料 |
| `jobs[].target_processing_time/energy` | 当前工艺为该 Job 设定的目标加工时间和能耗 |
| `jobs[].raw_tasks` | 解码后的路由，每项为若干 `[machine_id, processing_time]` |
| `jobs[].energy_tasks` | 解码后的加工能耗，每项为若干 `[machine_id, processing_energy]` |
| `jobs[].tasks` | Task 级详细配置，包括工序编码、类型、描述、基础值和机器选项 |
| `transport_time`、`transport_energy` | 当前工艺内部运输矩阵 |

后三工艺的固定 Task 编码如下：

| 工艺 | Task 编码与含义 |
| --- | --- |
| 焊装 | `W0` 齐套定位、`W1` 点焊、`W2` 填充焊/激光钎焊、`W3` 结构胶、`W4` 机械连接和密封、`W5` 检查 |
| 涂装 | `P0` 前处理电泳、`P1` 密封抗石击防腐、`P2` 底漆、`P3` 面漆、`P4` 清漆、`P5` 烘烤检查 |
| 总装 | `A0` 车门线束、`A1` 内饰座舱、`A2` 动力底盘、`A3` 能源模块、`A4` 玻璃座椅、`A5` 车轮外饰、`A6` 油液、`A7` 终检 |

当前主加载器不直接读取这些生成配置来构造 Job，而是以 `raw*/`、`add*/`、`delivery_cost/` 和物料文件为运行输入。修改调度行为时，不应只修改该目录。

## 5. 物料数据

### 5.1 物料主数据：`material_master.csv`

文件字段：

```text
material_id,material_name,unit,category
```

| 字段 | 含义 |
| --- | --- |
| `material_id` | 稳定的物料编号，被消耗和库存文件引用 |
| `material_name` | 中文物料名称 |
| `unit` | 计量单位：`piece`、`set`、`kg` 或 `L` |
| `category` | 所属工艺和物料类别 |

当前共有 43 种直接材料：

| 工艺类别 | 数量 | 作用 |
| --- | ---: | --- |
| 冲压板料 | 4 | 每个 Job 的冲压首道工序消耗 1 片板料 |
| 焊装材料 | 6 | 焊丝、结构胶、密封胶、铆钉、螺柱、螺栓螺母 |
| 涂装材料 | 12 | 电泳补加材料、PVC、UBC、空腔蜡、底漆及固化剂、面漆、清漆及固化剂 |
| 总装材料 | 21 | 模块、总成、动力系统、电池/燃油系统、油液和冷媒等 |

`piece` 和 `set` 按整数计量；`kg` 和 `L` 保留一位小数并向上取整。物料 ID 是唯一关联键，名称和单位只在主数据中维护。

### 5.2 `material_consumption/`：Job 与 Task 的直接物料需求

冲压使用 Job 级结构：

```json
{
  "instance": "example.fjs",
  "process_id": 1,
  "jobs": [
    {
      "job_id": 0,
      "materials": [
        {
          "material_id": "M1_STEEL_CR_LOW_CARBON",
          "quantity": 1.0
        }
      ]
    }
  ]
}
```

一个冲压 Job 只记录一次板料消耗，因为同一 Job 的多道冲压工序加工同一张在制品；首道工序负责领料。

焊装、涂装和总装使用 Task 级结构：

```json
{
  "instance": "example.fjs",
  "process_id": 2,
  "jobs": [
    {
      "job_id": 0,
      "tasks": [
        {
          "stage_operation_id": 2,
          "materials": [
            {
              "material_id": "M2_WELD_WIRE",
              "quantity": 0.8
            }
          ]
        }
      ]
    }
  ]
}
```

每个后三工艺 Task 都会出现在 `tasks` 中。不消耗直接材料的检查或状态工序使用空数组 `materials: []`，这表示“该工序没有直接物料扣减”，不表示数据缺失。

### 5.3 `material_configs/`：机器初始库存

每个实例、每个工艺都有一份库存文件：

```json
{
  "instance": "example.fjs",
  "process_id": 2,
  "machines": [
    {
      "machine_id": 1,
      "materials": [
        {
          "material_id": "M2_WELD_WIRE",
          "quantity": 5.8
        }
      ]
    }
  ]
}
```

该数据表示**运行开始时某台本地机器上已有多少某种物料**。每台机器都包含本工艺全部直接物料；未参与本实例初始 Task 的物料可以配置为 `0`。

初始库存按以下口径生成：

```text
目标库存 = ceil(
    该机器可加工的全部初始 Task 的物料需求之和
    × 1.20 / 计量精度
) × 计量精度
```

因此它覆盖初始 Job 在不同可选机器间分配时的需求波动，但不包含后续动态插入的 Job，也不等同于企业安全库存、仓库容量或自动补货策略。

### 5.4 物料数据的运行时含义

- `Machine.materials`：当前机器本地库存，结构为 `{material_id: quantity}`；
- `Job.material_consumption`：按 `stage_id` 保存该 Job 的 Job 级和 Task 级物料需求；
- `Task.material_consumption`：当前 Task 实际需要扣减的物料；
- `Task.material_consumption_committed`：该 Task 是否已经领料，避免开始事件重复扣减。

工序开始前会检查当前机器库存。库存足够时，按 Task 需求扣减并开始加工；库存不足时，工序进入等待，模拟器产生补料和恢复事件。默认补料到达时间为 20 个仿真时间单位，补料阈值为当前工序该物料需求的 3 倍；参数位于 `simulator_config.json`，不属于静态数据集本身。

## 6. 设备传感器流数据

### 6.1 数据服务与目录

设备数据位于 `datasets/simulator-data/`。它既是数据目录，也是一个 FastAPI 流式数据服务：

| 文件/目录 | 含义 |
| --- | --- |
| `data/anomaly.csv` | MetroPT 空压机真实故障基底，供机器数据合成使用 |
| `data/machines/machine_N.csv` | 每台设备的 17 列时序数据 |
| `config.yaml` | 数据生成、窗口契约、端口和展示配置 |
| `app/data/features.py` | 15 个模型输入特征及固定顺序的单一事实来源 |
| `app/data/generator.py` | 按确定性参数合成新机器数据 |
| `app/api/v1.py` | 窗口、展示帧、标签、预警和机器列表接口 |

主模拟器通过 `detection_data` 配置访问该服务，不直接解析 `machine_*.csv`。

### 6.2 机器文件规模

- 随包预生成：`machine_0.csv` 至 `machine_14.csv`，共 15 台；
- 每台数据行数：约 20,022–22,303 行；
- 可回放时间点数：约 9,962–11,102；
- 机器级故障时间点占比：约 1.57%–2.32%；
- 预生成文件原样读取；请求 `machine_id >= 15` 时，服务按固定种子确定性生成并落盘。

`timestamp` 从 0 开始，是行号或流内序号，不是 Unix 时间戳或现实日期时间。

### 6.3 CSV 字段

每行共有 17 列：

| 列 | 类型 | 量纲/含义 |
| --- | --- | --- |
| `timestamp` | 整数 | 行序号，从 0 递增 |
| `TP2` | 连续 | 压力，约 −0.026～10.526 bar |
| `TP3` | 连续 | 压力，约 8.032～10.174 bar |
| `H1` | 连续 | 压力，约 −0.028～10.182 bar |
| `DV_pressure` | 连续 | 压差，约 −0.022～5.992 bar |
| `Reservoirs` | 连续 | 储气罐压力，约 8.034～10.176 bar |
| `Oil_temperature` | 连续 | 油温，约 57.6～76.0 °C |
| `Motor_current` | 连续 | 电机电流，约 0.0375～6.3125 A |
| `COMP` | 二值 | 压缩机状态，0/1 |
| `DV_eletric` | 二值 | 电磁阀状态，0/1；字段拼写沿用源数据 |
| `Towers` | 二值 | 冷却塔状态，0/1 |
| `MPG` | 二值 | 源数据集保留的状态位，0/1 |
| `LPS` | 常量 | 在当前数据中恒为 0 |
| `Pressure_switch` | 二值 | 压力开关状态，0/1，绝大多数时间为 1 |
| `Oil_level` | 常量 | 在当前数据中恒为 1 |
| `Caudal_impulses` | 常量 | 在当前数据中恒为 1 |
| `label` | 二值 | 当前行是否为故障真值，0=正常，1=故障 |

模型输入特征固定为以下 15 列，顺序不可改变：

```text
TP2, TP3, H1, DV_pressure, Reservoirs,
Oil_temperature, Motor_current, COMP, DV_eletric,
Towers, MPG, LPS, Pressure_switch, Oil_level,
Caudal_impulses
```

`timestamp` 和 `label` 是辅助列，不进入模型窗口。`LPS`、`Oil_level`、`Caudal_impulses` 虽然无信息量，仍必须保留在 15 列模型中；前端展示时可以剔除。

### 6.4 时间点、窗口与标签

设备数据采用“1 个时间点=2 行”的约定：

```text
window_size = 100 行
step = 2 行/时间点
warmup_rows = 100 行
T = (总行数 - 100) // 2 + 1
window(t) = rows[2 × t : 2 × t + 100]
```

返回到模型的窗口形状为 `(100, 15)`，按通道优先送入模型时可组成 `(1, 15, 100)`。数据保持原始值，不做归一化。

相关标签含义：

| 标签 | 定义 | 含义 |
| --- | --- | --- |
| 行级 `label` | CSV 当前行的真值 | 当前采样行是否处于故障 |
| 时间点级 `label(t)` | 时间点 `t` 对应的 2 行中任一行为 1 | 当前时间点是否处于故障 |
| `warn(t)` | `[t, t+20)` 内是否出现故障 | 未来 20 个时间点内将发生故障的预警区 |

时间点标签使用预热后的行对齐：

```text
label(t) 对应 rows[100 + 2 × t : 102 + 2 × t]
```

`warn` 是展示和离线评估辅助标签，不应默认等同于已部署模型的训练目标。`label` 和 `warn` 都不能进入模型输入窗口，否则会造成标签泄漏。

### 6.5 基底合成方式

`data/anomaly.csv` 共有 4,040 行，其中 39 行标记为故障：

| 原始区间 | 行数 | 内容 |
| --- | ---: | --- |
| 0–1999 | 2,000 | 故障前正常段 |
| 2000–2019 | 20 | 异常段第 1 部分 |
| 2020–2038 | 19 | 异常段第 2 部分 |
| 2039–4039 | 2,001 | 故障后正常段 |

机器数据由正常段循环拼接、异常段随机截断插入和头尾正常保护段构成。相同配置和机器 ID 会生成相同数据，因此结果可复现。

### 6.6 与四工艺机器的对应关系

检测服务返回的 `machine_id` 是单台数据文件编号。模拟器按工艺把检测机器映射到调度机器：

```text
全局机器 ID = 当前工艺 machine_offset + 本地检测 machine_id
```

当前默认配置在 `simulator_config.json → detection_data` 中：

- `process_base_urls` 为工艺 1 和工艺 2 配置了检测服务；
- `process_protocols` 中工艺 1 使用 `legacy`，工艺 2 使用 `mfddt`；
- 工艺 3、4 若没有配置服务，前端会显示检测源不可用；
- 四个工艺的检测时间起点分别为 0、1800、3600、5400。

传感器数据描述设备运行状态和故障真值；调度数据描述 Job、Task、机器能力和生产约束。两者通过“工艺 + 本地机器编号 + 仿真时间”关联。

## 8. 数据完整性与关联规则

当前快照中，以下目录按文件去掉扩展名后的实例名与 `raw/` 完全一致，均为 309 组：

```text
add/
raw1/ add1/
raw2/ add2/
raw3/ add3/
delivery_cost/
process_generation_configs/process_1 .. process_4/
material_consumption/process_1 .. process_4/
material_configs/process_1 .. process_4/
```

加载器会进行以下关键校验：

- 四工艺 Job 数必须一致；
- `add` 的 Job/Task/机器选项集合必须与对应 `raw` 一致；
- 加工时间必须为正，机器编号必须存在；
- 交付文件行数必须等于 Job 数，且每行必须有 5 个字段；
- 运输时间、运输能耗必须是方阵、对角线为 0 且对称；
- 物料库存和消耗必须同时存在，Job 集合必须完整；
- 库存中必须包含消耗数据引用到的所有物料；
- 物料数量必须非负，物料 ID 不能重复。

## 9. 常见误用点

1. **不要把 `manifest.json` 的 550 当作当前可选实例数。**当前实际运行集是 309 个 FJSP 实例。
2. **不要用 `process_generation_configs` 代替 `raw/add`。**前者用于追溯；后者才是当前加载器的调度输入。
3. **不要混用本地机器 ID 和全局机器 ID。**调度表、事件日志和甘特图使用全局 ID；单工艺文件和检测服务通常使用本地 ID。
4. **不要把能耗当作现实 kWh。**当前加工和运输能耗是用于优化比较的相对单位。
5. **不要把 `label` 放入模型特征。**设备模型输入只包含固定顺序的 15 个特征。
6. **不要把 `warn` 当作已确认的训练标签。**它表示未来 20 个时间点内存在故障，需与具体模型的目标定义对齐。
7. **不要在修改一个工艺文件后忽略同名文件。**实例由多个同名文件共同组成，任何阶段缺失或规模不一致都会破坏四工艺链。
8. **不要把物料库存解释为安全库存。**它是初始线边库存，按初始 Task 需求和 1.20 倍预留生成；动态 Job 不在该基线内。
9. **不要依赖 `data_103.csv` 驱动当前仿真。**当前代码未引用该文件。
