## 0. 一句话目标

现在的「运行测试 → 完整运行结果」是一个折叠的 JSON，能证明"跑过了"，但**不能回答这个模型能不能用**。
这个页面要让人在 3 秒内回答三个问题：

1. **它准不准** —— F1 / PR-AUC / 混淆矩阵
2. **它真的能提前预警吗** —— 3 次故障里提前报了几次、提前多久、漏了几次
3. **它会不会乱报** —— 误报几段、多长、最长一段多久

第 2、3 点比 F1 更重要，因为 F1 高不代表能预警（实测：F1 0.79，但 3 次故障只有 1 次是真提前报出的）。

## 1. 先分清两种"测试"

界面上只有一个「运行测试」按钮，但实际是两种完全不同粒度的测试，要分开设计，否则前端会拿到一堆不该混在一起的数据。

| | **A. 单点测试** | **B. 全量评估** |
|---|---|---|
| 输入 | 数据集 + 时间点 `t` | 数据集 + 模型版本 |
| 算什么 | 取 `[t-window, t]` 一个窗口喂模型，出 1 个概率 | 整段测试集 43,637 个窗口全部推理，算指标 |
| 输出 | 1 个概率 + 1 个判定 | 混淆矩阵 / F1 / 事件诊断 / 曲线 |
| 耗时 | 单次推理 ~10 ms（走模拟器 `/predict`） | 离线一次算好（本方案用预生成数据包） |
| 用途 | 演示"这一刻模型看到了什么" | 论证"这个模型值不值得上线" |

**建议交互**：同一个按钮，跑完后页面分两块呈现上面两块结果；不要把单点概率塞进全量指标里。

## 2. 参数清单

分三组。**第一组是用户能改的，第二三组是只读展示的**——契约参数（window/horizon/stride）一旦可改，历史结果就不可比，必须只读。

### 2.1 输入参数（可交互）

| 参数 | 控件 | 示例值 | 取值 | 说明 |
|---|---|---|---|---|
| 测试数据集 | 下拉 | `冲压 · 单机` | 见下注 | 决定取哪份时序数据 |
| 模型版本 | 下拉 | `stage2__h20_nomix_ws160_s8` | `runs/` 下每个 run | 含权重 + 阈值 + 指标，切换即整套重绘 |
| 测试时间点 `t` | 时间输入 / 时间轴点选 | `2020-05-29 23:28:38` | 测试期任意窗口结束时刻 | 取 `[t-160步, t]` 输入模型 |
| 决策阈值 | 只读 + 悬浮说明 | `0.998357` | — | 验证集选定，测试集只评一次；想联动调整见 §4.3 |

> **关于「冲压 · 8 台」**：当前 8 台 / 30 台是同一份 MetroPT 单机数据（101 天）切块复制的，**模型对每台的指标完全相同**。
> 页面上建议标注"同一数据集切块，指标一致，不代表跨设备泛化能力"，否则评审会误以为做了 8 台交叉验证。

## 3. 可视化布局

按「结论 → 证据 → 诊断」三层，从上到下。不要一屏全塞，也不要只在底部放 JSON。

```
┌─ 参数条（§2.1 输入 + §2.2 契约） ─────────────────────┐
├─ ① 结论层：6 张 KPI 卡 ──────────────────────────────┤
├─ ② 单点证据：窗口热力图 + 关键通道折线 + 未来窗标签 ───┤
├─ ③ 全程时间轴（核心图，占整行） ─────────────────────┤
├─ ④ 三个故障事件放大（并排 3 张） ─────────────────────┤
├─ ⑤ 事件诊断表 | 误报清单 ────────────────────────────┤
├─ ⑥ 诊断层：阈值敏感性 | 输出分布 | 混淆矩阵 | PR | 训练曲线 ┤
└─ ⑦ 完整运行结果（保留现有折叠 JSON） ─────────────────┘
```

### ① 结论层 KPI（6 张卡，一行）

| 卡 | 主值 | 副文案 | 语义色 |
|---|---|---|---|
| F1 | `0.792` | P 0.706 / R 0.903 | 绿 |
| PR-AUC | `0.838` | 阈值无关的排序质量 | 中性 |
| 报警率 | `3.13%` | 共 1,366 个窗口报警 | 中性 |
| 事件召回 | `1/3` | 提前 1 · 晚报 1 · 漏报 1 | **橙** |

> 「事件召回 1/3」必须用橙色，不能和 F1 一样用绿色。这是全套图里最重要的一个"不好看但真实"的数字。

### ② 单点测试：模型看到了什么

三块横向排布，左边是**测试用例选择器**（正常 / 提前 / 晚报 / 漏报 / 误报 各一例），右边是证据图。

**(a) 15 × 160 热力图**
- 行 = 15 个通道（`TP2, TP3, H1, DV_pressure, Reservoirs, Oil_temperature, Motor_current, COMP, DV_eletric, Towers, MPG, LPS, Pressure_switch, Oil_level, Caudal_impulses`）
- 列 = 160 个时间步（标注 `-1600s … 0s`）
- 色 = 窗口内 z-score，截断 ±3，蓝—深灰—红发散色阶
- 常量通道（`LPS` / `Oil_level` / `Caudal_impulses`）标灰，避免读者以为"没变化是异常"

**(b) 关键通道折线（4 条）**
`TP2` / `DV_pressure` / `Oil_temperature` / `Motor_current`，每条 160 步曲线 + 右侧灰红区标注未来 20 步。
目的是让非算法同学看懂"模型输入长什么样"，不要放全部 15 条（会变面条）。

**(c) 未来窗标签条**
20 个方格，灰/红，配文"未来 200 s 内 12/20 步为故障 → 标签 = 1"。
这是解释"预测标签怎么来的"的唯一机会，必须有。

### ③ 全程时间轴（核心图，整行宽，高 ~250px）

横轴 101 天（2020-05-01 → 09-01），四层堆叠：

| 层 | 内容 | 编码 |
|---|---|---|
| 主图 | 故障概率 | 青绿折线 + 半透明填充，y ∈ [0,1]，网格 0/0.25/0.5/0.75/1 |
| 参考线 | 阈值 0.9984 | 橙色虚线，标注「距顶 0.16%」 |
| 底条 1 | 真实故障 | 3 个红块（5/29 23:30–5/30 06:00、6/5 10:00–6/7 14:30、7/15 14:30–19:00） |
| 底条 2 | 模型告警段 | 8 段：命中 4 段红、误报 4 段灰 |

**必须用 min/max 包络，不要用普通折线**（原因见 §6.1）。伪码：

```js
// 后端已按 2400 桶算好：t[i], prob_min[i], prob_max[i], alarm[i], label[i]
// 每桶 ≈ 60 min
for (let i = 0; i < n; i++) {
  const x = X(t[i]);
  ctx.moveTo(x, Y(prob_min[i]));
  ctx.lineTo(x, Y(prob_max[i]));   // 竖线 = 该时段概率取值范围
}
// 再把 prob_max 连成上包络，下面填充渐变
```

交互：悬停显示「桶起始时刻 / 概率 max·min / 是否曾告警 / 真值」；点击可回填 §2.1 的测试时间点。

### ④ 三个故障事件放大（并排 3 张）

每张：横轴 = `[onset-3h, min(end, onset+6h)]`，纵轴概率，标 onset 竖线，故障区间浅红底，告警段淡色底。
卡片标题直接写结论：

| 卡 | 标题文案 | 颜色 |
|---|---|---|
| #1 | 故障 #1 `提前告警` 提前 1.5 min 报出 | 绿 |
| #2 | 故障 #2 `晚报` 故障开始 3.5 min 后才报 | 橙 |
| #3 | 故障 #3 `漏报` 整段漏报 | 红 |

**这三张图必须用原始分辨率数据**（每 20 步一个点），不能用 ③ 的降采样序列，否则台阶会被拉成斜线，1.5 min 的提前量看起来像十几分钟（实测踩过这个坑，见 §6.2）。

### ⑤ 事件诊断表 + 误报清单

**事件表**（编号按测试期内出现顺序，对应 `REPORT.md` 的故障 #2 / #3 / #4）

| 故障 | 时段 | 时长 | 结果 | 提前/滞后 |
|---|---|---|---|---|
| #1 | 05-29 23:30 → 05-30 06:00 | 6.56 h | 提前告警 | **+1.5 min** |
| #2 | 06-05 10:00 → 06-07 14:30 | 48.1 h | 晚报 | **−3.5 min** |
| #3 | 07-15 14:30 → 07-15 19:00 | 4.51 h | 漏报 | — |

> `−3.5 min` 为本数据包口径（告警段起点 10:03:32 vs 故障起点 10:00:04）；
> `REPORT.md` 记作 3.6 min，差异来自窗口粒度（stride 20 步 = 200 s），不是两个结论。

**误报表**

| 起始 | 结束 | 持续 | 占比 |
|---|---|---|---|
| 05-13 14:13 | 05-13 14:36 | 0.39 h | 2% |
| 05-14 01:15 | 05-14 01:15 | 0.00 h | 0% |
| **05-19 22:43** | **05-20 22:55** | **21.28 h** | **96%** |
| 06-08 12:45 | 06-08 13:41 | 0.39 h | 2% |

### ⑥ 诊断层（5 张，决定"这个数能不能信"）

| 图 | 形式 | 要说明的事 |
|---|---|---|
| **阈值敏感性** | 两段折线（0.50–0.998 平坦区；0.998–0.9999 悬崖区），三条线 F1/P/R | 阈值挪 0.0001 就崩，可用区间只有 ~0.0004 宽 |
| **输出分布** | 50 桶双色柱状，纵轴**对数** | 正样本 91.3% 落在 ≥0.96，负样本 98.6% 落在 <0.04，中间几乎空 → 解释悬崖成因 |

| **PR 曲线** | recall–precision 曲线 + 工作点红点 + 随机基线 | AP 0.838，工作点还有上移空间 |
| **训练曲线** | loss / val F1 / val AP 三小图，标 best epoch | 训练 57 s，epoch 18 后饱和，再加 epoch 不改变结论 |

### 4.2 几个字段的口径（容易做错）

| 字段 | 口径 |
|---|---|
| `prob` | 模型 sigmoid 原始输出，**不做任何缩放** |
| `target` | 窗口标签 = 未来 `[t+1, t+1+H)` 内是否出现故障，**不是** t 时刻是否在故障中 |
| `label`（trace 内） | 桶内是否含故障窗口（`any`），用于底部真值条 |
| `status` | `early` = onset 前告警；`late` = onset 后才告警；`missed` = 整段无告警 |
| `lead_minutes` | 正数 = 提前几分钟；`delay_minutes` 正数 = 滞后几分钟 |
| `false_alarm` | 该告警段与任何 `[onset-H, fault_end]` 都不重叠 |

### 4.3 如果要做"阈值可调"

只重算告警判定，**不要重算指标卡**（指标必须对应导出阈值，否则不可复现）。做法：
- 前端用 `trace.prob_max >= 新阈值` 重新着色告警段
- KPI 卡固定显示导出阈值的数值，旁边加一句"当前预览阈值 0.9980（仅影响色块，不影响指标）"
- 阈值滑块范围限定 `[0.9980, 0.9990]`，超出直接提示"模型在此外无效"（见 §6.3）

## 6. 五个必须避开的坑（都是实测踩到的）

### 6.1 双峰输出：普通折线会把 40 分钟的脉冲画成跨天的宽峰

43637 个概率点里，91.3% 的正样本 ≥0.96、98.6% 的负样本 <0.04。任何降采样（LTTB/等距抽稀）在 101 天量级上都会把短暂告警拉宽。
**解法**：按桶取 `min/max`（本方案 2400 桶 ≈ 60 min/桶），画竖线 + 上包络。实测这样做 5/13 那次 23 分钟的误报才显示为一条细线，而不是一片色块。

### 6.2 事件放大图不能用降采样序列

用降采样序列画事件 #1 时，因为相邻点相隔 13 分钟，图上"提前 1.5 min"看起来像"提前 13 分钟"——直接把结论说反。
**解法**：`events[].series` 单独存该区间的原始分辨率点（stride=20 步，约 170 点/事件）。

### 6.3 阈值悬崖：可用区间只有 4e-4 宽

| 阈值 | F1 |
|---|---|
| 0.9983 | 0.786 |
| **0.9984** | **0.795** ← 最优 |
| 0.9985 | 0.246 |
| 0.9986 | **0.000** |

阈值往右挪 0.0002 就从 0.79 掉到 0。**页面必须把这件事显式画出来**（阈值敏感性图），否则读者会以为 0.79 是个稳健的结论。

### 6.4 事件级指标只有 3 个样本，别做百分比饼图

3 次故障 → 事件召回只能取 0 / 33% / 67% / 100%。做成"33% 的故障被提前预警"的环形图会严重误导。
**解法**：用 `1/3` 这种分数直述，配合三态标签（提前/晚报/漏报），不要画百分比。

### 6.5 正样本 2.45%，禁用 accuracy 与 ROC 主轴

全预测"正常"的 accuracy 是 97.6%，毫无意义。主指标固定用 F1 + PR-AUC；ROC-AUC（0.974）只作为附属数字，不作为主图。

## 7. 实现优先级

| 级别 | 内容 | 理由 |
|---|---|---|
| **P0** | 参数条（§2.1+2.2）、KPI 6 卡、全程时间轴、事件诊断表、误报清单 | 没有这些回答不了 §0 的三个问题 |

| **P2** | 输出分布、PR 曲线、训练曲线、完整 JSON 折叠 | 加分项，给技术评审看 |

工作量参考：P0 约 1.5 天，P1 约 1.5 天，P2 约 1 天（含联调）。
